# 注释检查技能（comments-check）— 设计文档

- **日期**：2026-08-09
- **状态**：方案已确认，待实现（用户已逐条拍板）
- **存放位置**：`.claude/skills/comments-check/`

---

## 一、目标

开发一个 Claude Code 技能 `comments-check`，让用户一句话就能给全项目代码做一次「注释体检」：
查出哪些注释**缺失**、哪些注释**和代码对不上**、哪些注释**小白看不懂**，并给出修改建议。
技能只「检查 + 报告」，**绝不修改任何代码**。

## 二、需求（用户已确认）

| 项目 | 决定 | 大白话说明 |
|---|---|---|
| 要求 1 | 注释够不够 | 每个函数、每段重要核心代码都应有详细注释，目标约 **3 行注释 : 7 行代码正文**（比例约 30%） |
| 要求 2 | 注释对不对 | 注释内容要和代码实际做的一致；注释里提到的名字在代码里必须还存在 |
| 要求 3 | 小白能看懂 | 注释要用大白话，解释「为什么这么做」，不堆术语 |
| 检查机制 | **脚本 + AI 混合**（用户选定） | 脚本算客观数字，AI 做主观点评 |
| 报告形式 | **聊天显示 + 存报告文件**（用户选定） | 聊天里总结 + 存一份 Markdown 到 `docs/注释检查报告-日期.md` |
| 检查范围 | 全项目体检（用户选定） | 根目录 *.js、src/**、test/**；跳过 node_modules/dist/.git 等 |

## 三、检查标准

1. **注释比例目标**：约 3 行注释 : 7 行代码正文 → 目标比例 **30%**。
   - 状态分级：≥30% 达标 ｜ 20%~30% 略低于目标 ｜ <20% 明显不足。
2. **「注释不对」的定义**（AI 判断）：
   - 注释说的和代码做的不一致（例：代码在求和，注释却写"求平均值"）；
   - 注释里提到的名字（变量/函数/参数）在代码里已经不存在了；
   - 注释照抄旧行为，没跟着代码更新。
3. **「小白视角」的定义**（AI 判断）：
   - 用大白话，优先解释「为什么这么做」；
   - 出现专业术语要顺带解释；
   - 不堆英文术语。

## 四、工作流程（三步）

1. **脚本数客观数字**：`node .claude/skills/comments-check/scripts/comment-stats.js`
   算出每个文件的：总行数、代码行数、注释行数、注释比例、状态，以及「头顶没写注释的函数」清单。
2. **AI 通读 + 主观点评**：按脚本点名的文件/函数重点读，逐条核对 3 个标准，
   并补查脚本查不到的重要核心代码（关键 if 分支、复杂循环、IPC 接口、SQL 语句）。
3. **写报告**：聊天里一句总结 + 逐文件问题清单；并存一份 Markdown 报告到 `docs/`。

## 五、技术实现

### 文件结构

```
.claude/skills/comments-check/
├── SKILL.md                  # 技能的「使用说明书」（frontmatter 含 name/description/context: fork）
└── scripts/
    └── comment-stats.js      # 客观数据统计脚本（零依赖，纯 Node 自带）
```

- `context: fork`：技能在独立小助手（subagent）里运行，与主对话隔离，自带检查工具。
- 脚本零依赖：只用 `fs` / `path`，不装任何东西，可随时 `node` 直接跑。

### comment-stats.js 要点

- 递归扫描项目，跳过 `node_modules` / `dist` / `.git` / `.claude` / `docs` 等非手写目录。
- 只统计 `.js` / `.html` / `.css`。
- 逐行分类「代码 / 注释 / 空行」，区分三种注释语法：
  - JS：`//` 行注释、`/* */` 块注释（识别引号，避免把字符串里的 `//` 误判成注释）；
  - HTML：`<!-- -->`；
  - CSS：`/* */`。
- 函数识别（JS）：`function 名字(`、`const 名字 = (...) =>`、`module.exports.名字 =`；
  往前找最近 3 行判断头顶有没有注释（空行跳过）。
- 输出：屏幕打印总览表 + 一段完整 JSON（供 AI 写报告用）。

### SKILL.md 要点

- 复述 3 条检查标准和红线（绝不改代码、不装东西、不碰真实账本数据、不扩大范围、命令一条一条跑）。
- 规定报告格式：总览 → 各文件体检表 → 需要改进的地方（文件/函数/行号/问题/建议）→ 做得好的文件 → 下一步建议。

## 六、边界情况

| 情况 | 处理 |
|---|---|
| 文件为空 | 代码+注释为 0，比例记 0，AI 点评时忽略 |
| 字符串里的 `//`（如网址） | 按引号识别跳过，不误判为注释 |
| 多行块注释 | 每行都计为注释行；`*/ 代码` 同行时按代码行计 |
| HTML / CSS 注释语法不同 | 按扩展名分别处理 |
| 匿名回调函数（如 `test('x', () => {})`） | 不列入「函数清单」，不算漏注释 |
| 中文文件名/路径 | 脚本用相对路径输出，报告用 `/` 分隔 |

## 七、测试

1. 写好脚本后，在项目根目录跑一次，人工核对输出的行数、比例、函数清单与实际代码是否吻合。
2. 用已知注释良好的 `db.js`、`score.js` 对照：比例应达标、无注释函数应为空。
3. 用整包技能跑一次 `/comments-check`，检查报告是否完整、可读。

## 八、不在本次范围（YAGNI）

- **不自动修改注释**：只出问题清单，改不改由用户决定。
- 不做自定义阈值配置（v1 固定 30% / 20%）。
- 不做跨文件智能关联（如「这个函数在哪被调用」）。
- 不引入任何第三方库或下载资源。
- 不检查非代码文件（Markdown、JSON、锁文件）。
